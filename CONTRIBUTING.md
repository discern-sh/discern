# Contributing to discern

Thanks for wanting to improve discern. The project is founder-led: the maintainer sets its direction and reviews changes under a narrow promise. discern must work for projects in any stack without accumulating exceptions for one toolchain, domain, or workflow.

Bug fixes, performance improvements, and stack-neutral improvements are welcome. We usually decline behavior that serves one stack or use case. Bring the problem to an issue first. Existing documentation or project configuration may already solve it, and the discussion can establish whether the problem exposes a general design flaw.

## Start with an accepted issue

Every pull request starts with an issue that a maintainer has accepted. Open the issue before implementation, describe the problem and its impact, and wait for agreement on the direction. This puts design review before the expensive part and protects your time.

Use the change-proposal template for new behavior or interfaces. Bugs and setup failures have their own templates. A maintainer accepting the problem does not prescribe an implementation. It confirms that the project should solve it.

## Choose the smallest change

Use the smallest change that solves the accepted problem:

1. Explain existing behavior in the documentation, including how the current parts work together.
2. Solve the problem through existing project configuration, a Project Script, a Skill, or a supported agent integration.
3. Extend a configuration or integration point while preserving discern's shared defaults.
4. Change core behavior when the problem is stack-neutral and the earlier approaches cannot solve it.

Move down the list only when the earlier approach falls short. Explain the choice in the issue and pull request.

## Own every line

AI-assisted contributions are welcome. You are responsible for every line you submit, including lines generated by an AI tool. You must understand the change and be able to explain and defend its behavior, tests, and tradeoffs in review. Tool output does not transfer that responsibility.

## Use the gate as the contract

`discern done` is the contribution contract. Run it from the repository root on the final tree. If it is not green, the change is not ready.

The command owns the build, check, test, scope, and quality-standard details, so this guide does not duplicate them. Its diagnostics name the command that failed and what to do next. These pages cover the contributor workflow:

- [Getting started](project/map/80-development/getting-started.md)
- [Code conventions](project/map/80-development/code-conventions.md)
- [Testing](project/map/80-development/testing.md)

Keep each commit to one logical change. Use an imperative subject and explain the reason for non-trivial work in the commit body.

## Sign your work

Sign every commit with `git commit -s`. The sign-off certifies the [Developer Certificate of Origin 1.1](https://developercertificate.org/) and records that you have the right to submit the work.

Inbound and outbound contributions use Apache-2.0. By submitting a contribution, you agree that the project may distribute it under the terms in [LICENSE](LICENSE). A Contributor License Agreement is not required.

## Report bugs and security issues

Open a bug or setup-failure issue with the matching template and include the complete `discern doctor --json` result. Report vulnerabilities through the private process in [SECURITY.md](SECURITY.md).
