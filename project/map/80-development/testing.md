# Testing

_How this repository's tests are written, how they run, and which patterns the Gate requires._

The project's final quality check (the Gate) runs the `test` job from `discern.toml`. This page explains how to write tests that pass it and how to run them while iterating. GitHub Actions runs the full Gate on Ubuntu for every pull request and push to `main`. The native Apple-silicon lane joins those events when the repository is public. While it is private, the Apple-silicon release row runs the same Gate before compiling. A newer commit on the same Git reference cancels an in-progress remote Gate because its result would describe an obsolete tree.

## How tests run

The suite is plain `deno test`, wired as the `test` job:

```sh
deno task test                                   # full suite (what the Gate runs)
deno task test tests/upgrade_migrations_test.ts  # a single file while iterating
deno task test --filter "convergence"            # a filtered subset by test name
```

`deno task test` first opens and closes a temporary `127.0.0.1` listener, then runs the suite with `--parallel` and `--allow-read --allow-write --allow-env --allow-run`. The local network probe exercises the same capability as the suite's process-interruption and site journeys; a sandbox denial therefore stops before the suite starts. The task then enters the fleet cap through `discern queue`; Deno appends a file or `--filter` argument to the wrapped command. Local discern Gates use the JUnit report format for structured diagnostics. Hosted Gates and bare tasks use Deno's pretty reporter. Both run the same tests. The suite invokes the Engine through `deno run src/main.ts` and shells out to Git. Deno runs test modules in parallel; tests inside one module remain serial.

This repository sets `[gate].concurrent_test_runs = 2`. Across the main checkout and every linked worktree, no more than two `done`, `test`, or measuring `standards` test-stage groups run at once. The cap schedules whole runs. Deno's worker parallelism inside each run is unchanged.

The site tests read the built site, which the Gate's build stage produces through `deno task site:build`. On a fresh checkout that has never run the Gate, run `deno task site:build` before the full suite. The `test.exclude` list in `deno.json` keeps generated output, distribution files, templates, and fixtures out of discovery.

Tests work at these layers:

- **In-process tests** call the production parser, planner, result core, or renderer that owns a decision. Put input variants here and drive them from a table when they share one contract.
- **Installer tests** drive the Deno command-line interface (CLI) as a real subprocess through `runCli` ([tests/helpers.ts](../../../tests/helpers.ts)). They exercise Cliffy parsing, global flags, JSON and Markdown result output, and exit codes through the CLI boundary.
- **Engine tests** (`tests/engine_*`) scaffold the real `templates/` directory, including the `discern.toml` seed, into a temporary directory through the installer's plan and apply path. They then run the Engine as a real subprocess through `runAgent` ([tests/engine_helpers.ts](../../../tests/engine_helpers.ts)). Each test runs `deno run src/main.ts <verb>` inside that directory, with a `discern` shim on `PATH` so Project Scripts resolve. The tests exercise Engine verbs such as `done` and `worktree`, including their JSON and Markdown result contracts, against a faithful install.

**Keep tests independent.** Every test works inside a fresh `withTempDir` directory. When it needs Git, it uses a repository from `gitInit` with its own config, no signing, and a `main` branch, which prevents global Git settings from affecting it. `engineEnv` also injects a suite-scoped `TMPDIR` into every spawned Engine. Job artifacts and fallback shims then use a per-run home that is removed at process exit instead of the shared operating-system temporary directory. Each scaffolded project's per-identity shim lives in its own `.git` directory and is removed with the scaffold ([ADR 0249](../_adr/0249-self-shims-cache-per-identity-sweep-pages-stay-budget-bounded.md)). Each test owns its fixtures, touches no shared state, and assumes no ordering. Keep all access inside the temporary directory and independent of other tests' side effects. The [Gate gotchas](done-gate-gotchas.md) explain what to check when a test passes alone but fails in the full run.

## How tests are written

- **Test each decision at its production seam.** Put a variant matrix in an in-process test, then keep a representative `runCli` or `runAgent` case for CLI parsing, output, exit codes, and boundary wiring. Each subprocess loads the CLI and may start Git or project commands, so reuse an existing boundary fixture when it already crosses the same path. The helpers disable color with `NO_COLOR`, so boundary assertions match plain text.
- **Scaffold from the real templates.** Engine tests use `scaffoldEngine` (which lays down `REAL_TEMPLATES` through `assembleInitPlan`/`applyPlan`), so the bytes under test are the bytes a real `discern setup` ships. Use `writeConfig` to set the `[jobs]`/`[scopes]`/`[standards]` a case needs, and `addWorktree` for the worktree-command layout.
- **Use fixtures for unit-level installer tests.** `FIXTURE_TEMPLATES` plus `testTokens` give a small synthetic tree for testing rendering/plan logic in isolation, separate from the full real templates.
- **Assert convergence where it matters.** `snapshotTree` and `assertConverges` express the invariant that upgrade output equals fresh-init output ([ADR 0014](../_adr/0014-versioned-migration-system.md)). Use them when a change touches the install, upgrade, or migration path.
- **Put coverage in the right place.** Test Engine behavior in `tests/engine_*_test.ts` and installer behavior in the other `tests/*_test.ts` files. Each Engine verb is exercised by a subprocess test through `runAgent`, so add a driving test in `tests/engine_*` for a new verb.
- **Own live subprocesses lexically.** Live Model Context Protocol (MCP) cases bind each server with `await using` in [`engine_mcp_test.ts`](../../../tests/engine_mcp_test.ts). The asynchronous disposer closes standard input, waits for cancellation, and escalates to process signals when shutdown stalls. A response timeout rejects only after that cleanup. A structural test refuses a future `spawnMcp` call without the disposal binding.
- **Start behavioral clocks and transitions at readiness.** Await tests observe a continuation marker written after the core captures its baseline before they mutate Git state ([tests/engine_await_test.ts](../../../tests/engine_await_test.ts)). A fixed sleep is not readiness evidence. [`tests/await_readiness_guard_test.ts`](../../../tests/await_readiness_guard_test.ts) scans every authored test module for that timing assumption. Process-level timeout tests follow the same rule: plant a marker when the behavior begins, wait for the marker or an early process exit, then start the elapsed-time assertion. Cold Engine startup has a separate readiness allowance, so machine load cannot spend the product behavior's deadline before the relevant job exists.
- **Keep the Map valid.** `tests/map_integrity_test.ts` validates every fenced `discern …` example against the live verb and flag registry, every intra-Map link and heading anchor against the shared renderer, and the published tiers' audience boundary. `tests/cli_reference_codegen_test.ts` holds the generated CLI reference to the registry. Quote exact commands and paths; the Gate checks them ([ADR 0146](../_adr/0146-docs-integrity-gate-and-generated-cli-reference.md)).
- **Use vocabulary from the term registry.** Synonyms retired by an entry are banned from every live surface by `tests/vocab_drift_test.ts`. Every known job, stage, and top-level verb must be named by the glossary or recorded absent with its reason by `tests/glossary_enrolment_test.ts`. The `vocabulary` Standard holds dead terms and bold-faced redefinitions at zero. Link a term's entry (`**[term](../00-orientation/glossary.md#term)**`) instead of restating it ([ADR 0167](../_adr/0167-term-registry-polices-the-vocabulary.md)).
- **Keep the feature account aligned with the feature registry.** A feature-canon node must claim every top-level verb, known job, stage, config table, bundled Skill, and agent provider, or record its absence with a reason. Every claim must name a live member, and the committed canon page must match its generator (`tests/feature_canon_enrolment_test.ts`, `tests/feature_canon_codegen_test.ts`; [ADR 0175](../_adr/0175-the-feature-canon-compiles-from-a-feature-registry.md)).
- **Keep the canon's plain-language register aligned.** Every feature node carries a required `plain` account with type-checked `why` and agent parity. The committed plain page must match its generator. `tests/feature_canon_plain_register_test.ts` holds the register: a plain lexicon paired with the glossary, plus a jargon scan over every plain string outside code spans. A new term fails until its plain rendering is decided. The `plain_reading_grade` Standard holds simplicity as a falling ceiling ([ADR 0228](../_adr/0228-the-feature-canon-carries-a-plain-language-register.md)).
- **Keep the benefit canon commercially useful and covering.** Every feature node is cited by a benefit entry's `drawsOn` or recorded absent with its reason (a record that is also cited fails as stale), and every public claim in the brand ledger is carried by at least one benefit. A stranded citation fails. Each entry separates human value from the reason it follows, while the generated commercial body excludes claim slugs, evidence-class labels, and inline caveats (`tests/feature_canon_benefit_test.ts`; [ADR 0268](../_adr/0268-the-benefit-canon-transposes-the-feature-registry.md); [ADR 0270](../_adr/0270-the-benefit-canon-separates-value-from-claim-qualification.md)).
- **Keep the practice canon claimed and cited.** Every bundled Skill is claimed by a tenet or recorded absent with its reason, every upheld key, mechanism, and yield names a live member, every feature pillar and benefit cluster is claimed or recorded absent, and the committed pages must match their generator (`tests/practice_canon_enrolment_test.ts`; [ADR 0284](../_adr/0284-the-practice-canon-enumerates-the-tenets.md)).
- **Probe every dry-run path.** Every command path that registers `--dry-run` is enumerated from the built CLI tree through `dryRunCapableVerbs` in [src/main.ts](../../../src/main.ts). `tests/engine_plan_parity_test.ts` drives a fail-closed fixture table over that set. A dry run must write nothing except its own Logbook record, and apply may perform nothing its plan omitted. A new verb that registers the flag fails the Gate until it carries a probe ([ADR 0027](../_adr/0027-plan-apply-engine-execution.md)).
- **Check formatter idempotence.** `tests/engine_tidy_test.ts` checks the real Map and root config for idempotence, scope selection, dry-run behavior, parse-before-write safety, missing paths, fenced code, and the frontmatter contract. A leading block that does not parse makes the formatter refuse the file; a valid block comes through unchanged ([ADR 0184](../_adr/0184-markdown-writers-preserve-or-refuse-frontmatter.md)). Every production config-writer test follows its mutation with a tidy no-op assertion. The canonical-set guard does the same for generated Map pages ([ADR 0178](../_adr/0178-discern-tidy-is-the-embedded-convention-for-discern-owned-surfaces.md)).
- **Declare every canonical set.** A canonical set is a member list with one source, guards, and generated artifacts. [`scripts/canonical_sets.ts`](../../../scripts/canonical_sets.ts) declares each one. `tests/canonical_sets_enrolment_test.ts` proves those declarations against the tree and sweeps conventionally named guard tests and codegen targets for strays ([ADR 0176](../_adr/0176-the-closed-sets-are-a-closed-set.md)). `tests/ssot_claim_guard_test.ts` reads each single-source-of-truth claim: a module with such a claim in its documentation comments must be a declared set's source or a recorded absence in `UNAFFILIATED_SETS` ([ADR 0181](../_adr/0181-an-ssot-claim-must-anchor-a-declared-canonical-set.md)).
- **Give environment-variable contracts one authority.** [`DISCERN_ENVIRONMENT_VARIABLE_DEFINITIONS`](../../../src/shared/environment_variables.ts) records every repository `DISCERN_*` contract with its purpose group, lifecycle, and public-documentation policy. Runtime application programming interfaces (APIs) and the experimental subset derive their names from it. [`tests/environment_variables_enrolment_test.ts`](../../../tests/environment_variables_enrolment_test.ts) scans carriers that cannot import the definitions. [`tests/environment_variables_codegen_test.ts`](../../../tests/environment_variables_codegen_test.ts) holds the generated public reference current, proves future public and internal members follow their policy, and keeps internal names out of every published Map tier ([ADR 0258](../_adr/0258-every-discern-environment-contract-has-one-membership-authority.md)).
- **Connect every shipped validator to production.** Each `src/lib` validator of a configured authored artifact is declared in [`tests/validator_registry.ts`](../../../tests/validator_registry.ts). A validator is either shipped, with a caller reachable from the binary's shipped trees and proven against the import graph, or repository-local with a reason. `tests/validator_enrolment_test.ts` sweeps every library function that a self-hosting test applies. It fails an unwired validator with the recovery action, so a check written for every project cannot remain active only in this repository's tests ([ADR 0201](../_adr/0201-artifact-validators-ship-or-record-their-exemption.md)).
- **Release artifacts execute before upload.** [`scripts/build_targets.ts`](../../../scripts/build_targets.ts) is the release target registry. Each native runner enters the generated matrix with the target and output name; the Apple-silicon row also selects the full gate before compilation. [`scripts/release_smoke.ts`](../../../scripts/release_smoke.ts) runs each compiled binary from a temporary directory, checks its version, embedded docs, exact first-party legal texts, and complete third-party notices, then scaffolds a fresh git repository from its embedded templates and proves it added no legal files. macOS jobs sign before the smoke and notarize before the checksum. [`tests/release_artifacts_test.ts`](../../../tests/release_artifacts_test.ts) auto-enrolls every target and proves a future target enters the same contract; [`tests/workflow_platform_test.ts`](../../../tests/workflow_platform_test.ts) binds the shared macOS action to routine and release CI and holds the release ordering.
- **Workflow dependencies are immutable.** [`tests/workflow_supply_chain_test.ts`](../../../tests/workflow_supply_chain_test.ts) scans every YAML file under `.github/workflows/` and refuses a remote action unless its ref is a full commit SHA. A new workflow or `uses:` step enrolls automatically. The same guard holds the release ordering: checksum, public build-provenance attestation, then artifact upload.

## Coverage

Line coverage of the repository's `src/` tree is measured by `deno task coverage` ([scripts/coverage.ts](../../../scripts/coverage.ts)). It runs the full suite under Deno's coverage instrument to collect raw profiles, makes a single lcov report pass, and prints one `DISCERN_METRIC coverage <pct>` line. [scripts/coverage_lib.ts](../../../scripts/coverage_lib.ts) anchors the lcov filter to `<repo>/src/`; a `src/` segment inside `node_modules` or a nested package does not count. [tests/coverage_lib_test.ts](../../../tests/coverage_lib_test.ts) pins that definition. The TypeScript Engine under `src/engine/` is instrumented with the rest of `src/`. The `engine_*` subprocess tests drive verbs through `src/main.ts`, so the installer and Engine share one coverage figure. Those processes make the run take minutes. Each leaves one V8 profile per loaded module, producing hundreds of thousands of small files per full run. The script limits the expensive reread to a single report pass.

That metric feeds `[standards.coverage]` in [discern.toml](../../../discern.toml), a floor that only rises. `discern standards` checks it. Because the measurement is slow, it runs outside the `discern done` Gate; continuous integration (CI) enforces it on every pull request. To raise the floor, add tests and capture the gain with `discern standards --pin`. The Standard's `margin` keeps the pinned floor a little below the measured value so ordinary drift does not trip it.

Terminal interaction is tested through real pseudo-terminals (TTYs). [`src/lib/terminal_interaction.ts`](../../../src/lib/terminal_interaction.ts) is the sole product choke point and maps admission, semantic groups and descriptions, values, stable searchable defaults, validation, completion, cancellation, and restoration into `@discern-sh/design-system@0.20.0` package requests. Its adapter tests require choice frames to use the available terminal width, leave one framed blank row above each group heading, disclose options hidden below the visible window, and keep product text free of terminal controls. [`interactive_tty_test.ts`](../../../tests/interactive_tty_test.ts) drives that production path through [`interactive_tty_harness.ts`](../../../tests/fixtures/interactive_tty_harness.ts), covering text, fixed confirmation geometry, selection markers, grouped and multiple selection, remembered search selection, repeated 16-row interaction cycles, tall text areas, Unicode editing, resize, modes with and without styling, Ctrl+C/EOF, and terminal restoration. Its 13-row composed-cycle journey is the smallest coherent frame with a six-row board header, one semantic group, one choice, and the authored hint; it proves that six-row board headers and four-row action preambles remain untouched while each package-fitted frame uses the largest window that fits the remaining viewport. The shared PTY driver accepts input only as phases that wait for one marker or an ordered marker sequence in newly observed child output. It refuses a phased plan that ends one write in a lone Escape byte while later input remains, because scheduler delay can turn an intended sequence prefix into cancellation; a test of an intentional lone Escape key press opts in explicitly. The EOF journey waits for the prompt's first read request, changes the terminal to canonical mode, and only then allows the production read to start and asks the parent for VEOF. A 600ms fixture startup delay keeps elapsed startup time out of that readiness contract. [`pty_process_test.ts`](../../../tests/pty_process_test.ts) independently proves both timing guards: a slow child receives Ctrl+C only after it has entered raw mode, and a delayed continuation after a lone Escape is rejected unless it declares that intent. [`docs_test.ts`](../../../tests/docs_test.ts) drives the real shared `discern docs` and `discern map` browser: title-first grouped search, the internal render-and-continue loop with remembered selection, explicit pager return and fallback, direct targets, and the complete static and machine projection matrix. [`terminal_test.ts`](../../../tests/terminal_test.ts) injects light, dark, timeout, environment-hint, and skipped-probe readings at the sole process boundary. Scripted Desk-runtime tests cover the product action loop; the Desk programme's future `desk_tty_harness.ts` will prove the complete package-backed application rather than reusing this generic interaction journey.
