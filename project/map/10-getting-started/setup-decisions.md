# The decisions setup asks you to make

_Setup turns one repository study into working conditions future coding sessions inherit. This page explains where your judgment matters._

## Choose the model for the repository study

discern sets no hard minimum model. It recommends the strongest suitable reasoning model because setup authors four lasting parts of the project:

- the Gate, which decides which quality checks run;
- the worktree policy, which keeps task work isolated and makes external resources ready;
- the Map, which tells later agents where to start and which boundaries matter;
- the project instructions every configured coding agent reads.

A stronger reasoning model is more likely to notice hidden boundaries, preserve workflows, and challenge false assumptions before they become shared context. That reduces later correction and repository reading.

Before you choose, the agent reports its current provider/model identifier when known, or `unreported`. This self-declared provenance is advisory; it does not prove capability.

To switch, select another model in your coding tool, open a fresh project session, and repeat the setup request. The current agent stops without writing. To continue here, say so plainly; setup records the reported provenance and proceeds.

## Know which choices remain yours

The agent handles routine, reversible authoring on the reviewable setup branch. It narrates each major stage and benefit without asking you to approve files one by one.

It waits when the repository cannot supply a consequential answer: missing product intent, a new dependency or paid service, conflicting owner instructions, the primary subsystem boundary, shared or durable data, broader access, or binary merge policy.

Each decision names:

- the outcome and why it matters;
- the recommended option;
- what each option changes;
- your action and the agent's next action;
- authority, reversibility, and recovery.

If a question lacks that context, ask the agent to re-serve the complete setup decision before answering.

## Review what later sessions will inherit

Before landing, the handoff explains the primary subsystem, starting point, boundary, non-obvious invariant, project principles, instruction sources, protections, and open items. Canonical Map, ledger, and job inventories support that account beside the exact Gate Proof.

Proof verifies the setup branch; it does not authorize landing. You may land, leave for review, or decline. Only after setup reaches the trunk should you open a fresh provider session and run the displayed activation check. Optional improvement follows a successful check.
